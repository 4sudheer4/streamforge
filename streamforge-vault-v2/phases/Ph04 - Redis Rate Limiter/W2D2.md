`HandlerInterceptor` is part of **Spring MVC**. It only runs after Spring has done a lot of work — parsed the request, found the right controller, resolved method arguments.

`Filter` is part of the **Servlet spec**. It runs before Spring MVC even wakes up.

**Why does this matter for a rate limiter?**

Think about what you want to happen when a request is rate limited. Do you want Spring to do all that work first — find the controller, resolve arguments — and THEN reject it? Or do you want to reject it as early as possible?

Reject at the earliest possible point. No point letting Spring MVC do work — find the controller, resolve arguments, build the context — for a request you're going to reject anyway.

Filter sits at the Servlet layer — before Spring MVC. Request gets killed there. Spring never wakes up.

This is why `OncePerRequestFilter` — it's Spring's base class for Servlet filters, guarantees the filter runs exactly once per request even in complex dispatch scenarios.

**Interview one-liner:**

> "Rate limiting belongs in a Servlet Filter not a HandlerInterceptor — reject before Spring MVC does any work, fail fast at the earliest point."

**W2D2 — RateLimitFilter + Response Headers**

---

**Core Concepts**

**HTTP Headers vs Request Body**

- Headers → infrastructure metadata. Rate limiting, auth, content-type, tracing. Read by filters, proxies, Nginx.
- Body → business data. Domain objects. Read by controllers and services.
- Rule: if Nginx needs to read it → header. If only your app needs it → body.

**Filter vs HandlerInterceptor**

- Filter = Servlet layer. Runs before Spring MVC wakes up.
- HandlerInterceptor = Spring MVC layer. Runs after controller is resolved.
- Rate limiting belongs in Filter — reject before Spring does any work. Fail fast.

**400 vs 429**

- 429 = you're allowed but exceeded limit. Slow down.
- 400 = malformed request. Fix your request.
- Missing `X-Source-Id` = we don't know who you are = 400, not 429.
- Always use the most accurate error code.

**`RateLimitResult` record**

- Immutable per instance. New instance created per request.
- Carries `allowed` and `remaining` between `SlidingWindowRateLimiter` and `RateLimitFilter`
- Same pattern as `StreamEvent` passed between `FingerprintGenerator` and `DeduplicationEngine`
- Public record required — return type of public method must be at least as visible as the method

**Single Redis call**

- Old code called `redisTemplate.execute()` twice — two ZADDs, two counts, request recorded twice
- One call returns count. Java calculates remaining. Never call Redis twice for the same decision.

**`X-RateLimit-Reset` approximation**

- Sliding window has no fixed reset time
- Send `now + windowMs` as approximation
- Strictly accurate reset requires knowing when oldest request in window expires

**FAANG Interview Questions — W2D2**

1. "Where in the request lifecycle should rate limiting happen and why?" → Servlet Filter, before Spring MVC, fail fast, reject before any work is done
2. "What's the difference between 400 and 429? When do you use each?" → 400 = malformed request, 429 = valid request but limit exceeded
3. "Your rate limiter adds 5ms latency to every request. How do you reduce it?" → Redis pipelining, async recording, token bucket algorithm
4. "How would you support different limits per customer tier?" → pass limit as ARGV to Lua, load from config/DB per sourceId
5. "What happens if Redis goes down?" → fail open (allow all) vs fail closed (deny all). Tradeoff. Circuit breaker pattern.

---

**Gotchas — W2D2**

- **`return` after error response** — forget `return` after 429 → `chain.doFilter()` runs anyway → `IllegalStateException: response already committed`
- **Reading body in filter** — body can only be read once in Servlet. Reading it in filter means controller can't read it. Use headers for filter-level decisions.
- **Double Redis call** — calling `execute()` twice records the request twice, inflates count, breaks accuracy
- **Horizontal scaling** — works perfectly with one instance locally. Always test behind load balancer in staging.
