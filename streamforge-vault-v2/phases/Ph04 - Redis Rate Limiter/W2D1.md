**Core Concepts**

**What Redis is and isn't**

- Not a page cache. Not a load balancer.
- In-memory data store — strings, lists, sorted sets, hashes, streams
- Here: shared state store for rate limit counters across all app instances
- Passive — never pushes. Only responds when asked.

**Why Redis over in-memory**

- 3 app instances + in-memory counter = 300 effective limit
- Redis = one sorted set, all instances share it = true 100 limit
- In-memory rate limiting breaks the moment you scale horizontally

**Fixed Window vs Sliding Window**

- Fixed window exploit: send 100 at 11:59:59, 100 at 12:00:00 = 200 in 2 seconds
- Sliding window: window is always `now - 60s`. No fixed boundary. No reset cliff.
- 100 requests at 12:00:59 → at 12:01:00 window still sees all 100 → denied

**Lua Atomicity**

- ZADD + ZREMRANGEBYSCORE + ZCOUNT = 3 separate commands
- Without atomicity: two concurrent requests both read 99, both proceed = 101 allowed
- Lua runs as single atomic operation inside Redis. No interleaving possible.
- Lua returns raw count. Java makes allow/deny decision. Single responsibility.

**Sorted Set mechanics**

- Key: `rl:source-abc` — always namespace Redis keys
- Member = timestamp, Score = timestamp — score enables range queries
- ZREMRANGEBYSCORE evicts by score range — deletes all timestamps older than `now - windowMs`
- ZCOUNT counts remaining — all entries left are within the window

**`@PostConstruct` vs `new`**

- `@PostConstruct` only fires when Spring manages the object
- `new` keyword bypasses Spring — `@PostConstruct` never runs
- Mock replaces entire `redisTemplate` — arguments to `execute()` ignored, Lua never loads

**`Long result == 1L` gotcha**

- Java caches `Long` objects only for -128 to 127
- `result == 1L` works accidentally for small numbers
- `Long.valueOf(1L).equals(result)` is always correct

**FAANG Interview Questions — W2D1**

1. "Design a rate limiter for a distributed system with 10 app instances." → Redis sorted set, Lua atomicity, sliding window, key namespacing
2. "Why not use a counter with TTL instead of a sorted set?" → fixed window boundary exploit, 200 requests in 2 seconds
3. "Why is Lua better than Redis MULTI/EXEC transactions?" → MULTI/EXEC doesn't guarantee atomicity under watch conflicts, Lua is truly atomic
4. "How would you test the race condition you prevented with Lua?" → concurrent threads, CountDownLatch, verify exactly 100 requests succeed

**Gotchas — W2D1**

- **Sorted set memory leak** — skip ZREMRANGEBYSCORE → grows forever → everyone rate limited permanently
- **Redis key collisions** — flat keyspace, always namespace: `rl:`, `cache:`, `session:`
- **`@PostConstruct` in tests** — Spring never starts with `new` → script stays null → mock swallows it anyway
- **Remaining count negative** — `Math.max(0, limit - count)` — never expose -1 to client
