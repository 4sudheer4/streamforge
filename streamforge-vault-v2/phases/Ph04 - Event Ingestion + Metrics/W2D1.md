**W2D1 — Redis Sliding Window Rate Limiter**

---

**What we built**

- `RedisConfig` — Lettuce connection factory, `RedisTemplate<String,String>` with `StringRedisSerializer`
- `rate_limit.lua` — atomic sliding window script in `src/main/resources/scripts/`
- `SlidingWindowRateLimiter` — loads Lua at startup via `@PostConstruct`, `tryAcquire(sourceId)` returns boolean
- `application.yml` — added `spring.data.redis.host/port`
- Unit test — mocks `RedisTemplate`, verifies `1L` → `true`, `0L` → `false`

---

**Core concepts owned**

- Fixed window boundary exploit — 200 requests in 2 seconds by straddling windows
- Sliding window — window is always `now - 60s`, no fixed boundary, no reset
- Redis sorted set — timestamp as both score and member, enables range eviction
- Lua atomicity — ZADD + ZREMRANGEBYSCORE + ZCOUNT as one indivisible operation
- Race condition without atomicity — two concurrent requests both read 99, both proceed
- Redis as shared state store — not a cache, not a load balancer, all instances talk to one source of truth
- `@PostConstruct` bypassed by `new` — Spring never starts in unit test
- Mock intercepts `execute()` — arguments ignored, `rateLimitScript` never needed

---

**Interview one-liner**

> "Sliding window rate limiter uses a Redis Sorted Set of timestamps — ZADD, ZREMRANGEBYSCORE, ZCOUNT in an atomic Lua script — shared across all instances to prevent race conditions and boundary exploits."
