### 1. Rate Stats Endpoint

#### Why It Exists

A fraud analyst at NFCU needs to monitor payment source behavior in real time. This endpoint exposes live traffic data for any source — current rate, historical max, rolling average, and spike history.


#### SpikeStats Record

java

```java
// src/main/java/com/streamforge/domain/SpikeStats.java
public record SpikeStats(
    String sourceId,
    long currentRate,    // requests in current second
    long maxInWindow,    // highest burst in last 60 seconds
    double rollingAvg,   // average rate over last 60 seconds
    long spikeCount,     // total spikes detected this session
    Instant lastSpikeAt  // nullable — null if no spike yet
) {}
```

**Why primitives (`long` not `Long`):** `Long` is nullable requiring null checks everywhere. `long` can't be null — safer for numeric fields. Only `lastSpikeAt` stays as `Instant` object because it genuinely can be null before any spike occurs.

---

#### SpikeDetector — New Fields and Methods

java

```java
// two new fields in SpikeDetector
private final Map<String, AtomicLong> spikeCounts = new ConcurrentHashMap<>();
private final Map<String, Instant> lastSpikeAt = new ConcurrentHashMap<>();
```

**Why `ConcurrentHashMap`:** Multiple threads could theoretically read stats while the scheduler writes spike data. Thread safe without locking the entire map.

Updated spike detection block in `flushBuckets()`:

java

```java
if (rollingAvg > 0 && bucketCount >= 5 && count > SPIKE_MULTIPLIER * rollingAvg) {
    // track spike history — inside if block only
    spikeCounts.computeIfAbsent(sourceId, k -> new AtomicLong(0)).incrementAndGet();
    lastSpikeAt.put(sourceId, Instant.now());
    
    // rest of spike handling...
}
```

**Why inside the if block:** You only increment `spikeCount` when a spike actually occurs. Incrementing outside would count every second as a spike.

`getStats()` method:

java

```java
public SpikeStats getStats(String sourceId) {
    long currentRate = Optional.ofNullable(currentBucketCount.get(sourceId))
        .map(AtomicLong::get)
        .orElse(0L);
    long maxInWindow = analyzer.getMaxInWindow(sourceId);
    double rollingAvg = analyzer.getRollingAvg(sourceId);
    long spikeCount = Optional.ofNullable(spikeCounts.get(sourceId))
        .map(AtomicLong::get)
        .orElse(0L);
    Instant lastSpike = lastSpikeAt.get(sourceId);

    return new SpikeStats(sourceId, currentRate, maxInWindow, 
                          rollingAvg, spikeCount, lastSpike);
}
```

**Why `Optional.ofNullable`:** A source that has never sent events won't exist in the maps. `Optional.ofNullable` handles the null case gracefully returning 0 instead of throwing `NullPointerException`.

#### AnalyticsController

java

```java
// src/main/java/com/streamforge/api/AnalyticsController.java
@RestController
@RequestMapping("/api/v1/analytics")
@RequiredArgsConstructor
public class AnalyticsController {

    private final SpikeDetector spikeDetector;

    @GetMapping("/rate-stats/{sourceId}")
    public ResponseEntity<SpikeStats> getRateStats(@PathVariable String sourceId) {
        SpikeStats result = spikeDetector.getStats(sourceId);
        return ResponseEntity.ok(result);
    }
}
```

**`@PathVariable` not `@RequestParam`:** `sourceId` is in the URL path `/rate-stats/{sourceId}` not a query string. `@RequestParam` would require `/rate-stats?sourceId=payment-service`.

#### RateLimitFilter — shouldNotFilter

```java
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    String path = request.getRequestURI();
    return path.startsWith("/api/v1/analytics") || 
           path.startsWith("/actuator") ||
           path.equals("/health");
}
```

**Why needed:** `RateLimitFilter` requires `X-Source-Id` header on every request. ### 2. DLQ — The Poison Pill Problem

#### What Problem DLQ Solves

Kafka partitions are strictly ordered. Consumer reads offset by offset:

```
Partition 4:
[offset 0] ✅ processed
[offset 1] ✅ processed
[offset 2] ❌ throws exception
[offset 3] ⏳ waiting forever
[offset 4] ⏳ waiting forever
```

Without DLQ — offset 2 retries forever. Offset 3, 4, 5 never process. Entire partition blocked by one bad message — called a **poison pill**.

```
With DLQ:
[offset 2] fails 3 times → routed to "dlq" → offset committed → consumer moves on
[offset 3] ✅ processed
[offset 4] ✅ processed
```

**Interview one-liner:** _"A poison pill at offset N blocks all subsequent messages in that partition forever — DLQ breaks this by routing failures after N retries, committing the offset, and unblocking the pipeline."_

---

#### DLQ Config in KafkaConfig.java

java

```java
@Bean
public DeadLetterPublishingRecoverer recoverer(
        KafkaTemplate<String, String> template) {
    return new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition("dlq", 0));
}

@Bean
public DefaultErrorHandler errorHandler(
        DeadLetterPublishingRecoverer recoverer) {
    return new DefaultErrorHandler(
        recoverer,
        new FixedBackOff(1000L, 3L)
    );
}

@Bean
public ConcurrentKafkaListenerContainerFactory<String, String>
        kafkaListenerContainerFactory(
        ConsumerFactory<String, String> consumerFactory,
        DefaultErrorHandler errorHandler) {
    ConcurrentKafkaListenerContainerFactory<String, String> factory =
        new ConcurrentKafkaListenerContainerFactory<>();
    factory.setConsumerFactory(
        (ConsumerFactory<? super String, ? super String>) consumerFactory);
    factory.setCommonErrorHandler(errorHandler);
    return factory;
}
```

**`DeadLetterPublishingRecoverer`:** Spring's built-in DLQ router. After all retries exhausted, takes the failed message and publishes to target topic. The lambda `(record, ex) -> new TopicPartition("dlq", 0)` always routes to partition 0 of `dlq` — single partition keeps failures in strict chronological order for debugging.

**`FixedBackOff(1000L, 3L)`:** 1000ms between retries, maximum 3 attempts. Total wait = 3 seconds before DLQ. Covers transient failures — brief network blips, momentary DB unavailability. `FixedBackOff` = constant wait. Alternative is `ExponentialBackOff(1000, 2.0)` = 1s, 2s, 4s — better for production to avoid thundering herd.

**`DefaultErrorHandler`:** Spring Kafka's modern error handler — replaces the old `SeekToCurrentErrorHandler`. Wraps your recoverer and backoff policy. Registered on `ConcurrentKafkaListenerContainerFactory` so every `@KafkaListener` in your app automatically gets retry + DLQ behavior without configuring each one separately.

**`ConcurrentKafkaListenerContainerFactory`:** The container that manages all `@KafkaListener` methods. By registering it as a `@Bean` with your error handler, every consumer inherits retry + DLQ automatically.

---

#### application.yml — Consumer Config

yaml

```yaml
spring:
  kafka:
    consumer:
      group-id: streamforge-consumer
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      auto-offset-reset: earliest
```

**`group-id`:** Kafka tracks which messages a consumer group has processed via committed offsets. All instances with the same group-id share the workload — each partition assigned to one instance. Different group-ids get independent copies of all messages.

**`StringDeserializer`:** Converts bytes back to String. Mirrors `StringSerializer` on the producer side. Key → String (sourceId), value → String (JSON).

**`auto-offset-reset: earliest`:** When a new consumer group starts with no committed offset, start from the beginning of the topic. Your consumers will process all events ever published — including ones from earlier testing sessions.

### 3. EventsConsumer

java

```java
// src/main/java/com/streamforge/infra/EventsConsumer.java
@Slf4j
@Component
public class EventsConsumer {

    @KafkaListener(
        topics = "events",
        groupId = "streamforge-consumer"
    )
    public void consume(ConsumerRecord<String, String> record) {
        log.info("EventsConsumer received: partition={} offset={} key={} value={}",
            record.partition(),
            record.offset(),
            record.key(),
            record.value());

        // temporary — remove after DLQ verified
        if (record.value().contains("\"type\":\"payment\"")) {
            throw new RuntimeException("Simulated processing failure for DLQ test");
        }

        log.info("EventsConsumer processed event key={}", record.key());
    }
}
```

**`@KafkaListener`:** Marks this method as a Kafka consumer. Spring automatically connects to Kafka, subscribes to `events` topic, polls for messages, and calls `consume()` for each one.

**`ConsumerRecord<String, String>`:** Full message envelope containing:

```
record.key()       = sourceId ("payment-service")
record.value()     = full StreamEvent JSON
record.offset()    = position in partition (0, 1, 2...)
record.partition() = which partition (0-11 for events topic)
record.topic()     = "events"
record.timestamp() = when message was produced
```

**Why `consume()` is the doorway:** Every event published to Kafka flows through this method. In production this is where business logic lives — fraud scoring, analytics updates, rule engine evaluation, downstream notifications. The DLQ safety net sits behind it automatically via `DefaultErrorHandler`.

**The intentional failure:** `throw new RuntimeException` simulates a real processing failure. Remove after DLQ is verified. In production, real failures come from Postgres being down, NPEs in business logic, schema mismatches, etc.

### 4. DLQConsumer

java

```java
// src/main/java/com/streamforge/infra/DLQConsumer.java
@Slf4j
@Component
public class DLQConsumer {

    @KafkaListener(
        topics = "dlq",
        groupId = "streamforge-dlq-consumer"
    )
    public void consume(ConsumerRecord<String, String> record) {
        log.error("DLQ message received — processing failed after retries: " +
            "topic={} partition={} offset={} key={} value={}",
            record.topic(),
            record.partition(),
            record.offset(),
            record.key(),
            record.value());
    }
}
```

**`groupId = "streamforge-dlq-consumer"`:** Separate consumer group from `EventsConsumer`. Each group maintains its own independent offset. Using the same group would cause Kafka to think DLQ messages were already processed by `EventsConsumer`.

**`log.error`:** DLQ messages represent failures that exhausted all retries. Error level ensures they appear in monitoring dashboards and trigger alerts. In production this would also send a PagerDuty alert.

**Never throws:** If `DLQConsumer` threw an exception, the message would retry and need another DLQ. A DLQ for your DLQ is a design smell. DLQ consumer's only job is logging — it always succeeds.

```
                      → EventKafkaProducer.publishEvent()

        ↓
(every second — background)
SpikeDetector.flushBuckets()
  → MonotonicDequeAnalyzer.record()
  → spike check
  → if spike → spikeCounts++ → lastSpikeAt=now
              → kafkaTemplate.send("anomalies", sourceId, payload) ✅
        ↓

  → DefaultErrorHandler retries 3x with 1s backoff

        ↓

  → log.error with full context ✅
        ↓

  → SpikeDetector.getStats()
  → returns SpikeStats {currentRate, maxInWindow, rollingAvg, spikeCount, lastSpikeAt} ✅
```

### Gotchas

**Gotcha 1 — Analytics endpoint blocked by RateLimitFilter:** `RateLimitFilter` requires `X-Source-Id` on every request. Override `shouldNotFilter()` to exclude analytics and actuator paths.

**Gotcha 2 — Same groupId for EventsConsumer and DLQConsumer:** If both use the same groupId, Kafka assigns partitions across both consumers. DLQ messages might never reach `DLQConsumer`. Always use separate groupIds for separate consumers.

**Gotcha 3 — DLQConsumer throwing exceptions:** If `DLQConsumer` fails, messages retry and eventually need another DLQ. DLQ consumer must never throw. Just log.

**Gotcha 4 — `auto-offset-reset: earliest` replaying old messages:** When app restarts with a new groupId or cleared offsets, `earliest` replays all messages from the beginning. Expected behavior for StreamForge. In production you'd use `latest` to only process new messages after deployment.

**Gotcha 5 — spikeCount resets on app restart:** `spikeCounts` is in-memory. App restart = count reset. Acceptable for StreamForge. In production persist to Postgres with a `spike_events` table.

### Interview Questions — W2D5

**"How does your DLQ work?"** _"Spring Kafka's `DefaultErrorHandler` retries failed messages 3 times with 1 second fixed backoff. After 3 failures, `DeadLetterPublishingRecoverer` publishes the message to our DLQ topic and commits the offset, unblocking the consumer to process subsequent messages."_

**"Why does the DLQ consumer never throw?"** _"If it threw, the message would retry and need another DLQ — a DLQ for your DLQ is a design smell. The DLQ consumer's only job is logging failures for ops visibility."_

**"How do you replay DLQ messages?"** _"You reset the consumer group offset on the DLQ topic back to 0. This replays all failed messages through a fixed consumer that processes them correctly. In production you'd build a replay endpoint that reads from DLQ and re-publishes to the original topic."_

**"Why separate groupIds for EventsConsumer and DLQConsumer?"** _"Kafka uses groupId to track offsets per consumer group. Same groupId would cause partition sharing between consumers — DLQ messages might route to EventsConsumer which would fail them again, creating an infinite loop."_

**"What's the difference between FixedBackOff and ExponentialBackOff?"** _"FixedBackOff waits a constant interval between retries — 1s, 1s, 1s. ExponentialBackOff doubles each time — 1s, 2s, 4s. Exponential is better for production because it reduces thundering herd — many consumers retrying simultaneously at fixed intervals can overwhelm a recovering downstream service."_
